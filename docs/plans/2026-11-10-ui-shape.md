# The UI's shape: one page shell, one list row, and the kind as the entry point

## At a glance

The two record pages of the client app — a customer and a product — are the same screen written
twice, and so are their two add screens. This piece writes each of them once, with the kind as
data, and in doing so builds the three pieces the code convention says must exist before any
client's own page can be anything but a copy. **Nothing a person sees changes**, which is the
proof: the picture run reads zero moved pixels. The cheapest path is reuse, not design — the list
page already draws both kinds from one body and one table of kinds (`ui/src/listSheet.ts`'s
`LISTS`), the detail cards are already shared parts, and the forms differ for real and stay. About
40 machine minutes over seven steps, one review, and one picture run in the human's terminal.

## The slice

One slice: five extractions in `ui/src`, each leaving the app walkable, then the documents that
describe the old shape, then the whole gate and the review. No behaviour moves at any step, so the
app does the same thing after each one and the existing tests say so. There is no new test suite:
`ui/src/pages/client/ListPage.test.tsx` already walks all four screens in 42 cases, and it must
stay green **unchanged** — a case edited to fit a refactor is the refactor marking its own homework.

## What the convention requires, and what today's tree already holds

The authority is `docs/conventions/code.md`'s **C3**, "Parameterise a second kind rather than copy
its screens", and the human's decision it points at, `docs/memo/divergence-and-caching.md`'s "Where
a client's difference lands", which requires:

> **Three extractions come before the first client page exists** — a piece, not a line: the page
> shell (title, action row, `Loaded` wrapper), written by hand twice today
> (`ui/src/ListPage.tsx#L22-L39`, `ui/src/StaffListPage.tsx#L156-L170`), as one component a client
> page takes; a list kind as the entry point, so a client's list is a new `LISTS` entry and not a
> copy of `ListPage`; and the row and detail pieces a client page would re-lay out, named and
> exported. _Why:_ until they exist a client page can only be a copy, so the commercial gate holds
> on that ground alone.

## The look: a picture run, and zero is the pass

Two walks draw every screen this piece touches: **`admin-lists`**, whose 21 screens are the two
lists, their imports, the two record pages and the two add pages; and **`piece-2`**, the staff walk,
because step 3 touches `PersonPage` and step 1 touches the staff list — `staff-1-list`,
`staff-10-save-conflict`, `staff-11-save-failed`, `staff-14-search`, `staff-16-field-refused`.

The run is the human's, in their own terminal: no browser starts in the machine's sandbox. It is
`bash walk/run.sh admin-lists piece-2` from the repository root, with no `--moved` and no
`--write`. **No screen is allowed to move**, so the
reading is `== verdict: green` with every raw pixel count 0, and any count above 0 is this piece
being wrong rather than a base needing a rewrite. That reverses how a run is usually read, and it
is why `--write` must not be passed.

## The human's point

**One. The screens did not change — and that is the whole result.** After step 8 the human runs the
two walks above and reads the verdict line. Green with nothing moved means the customer and product
pages, their add screens and the staff list are pixel for pixel what they were this morning, while
the code behind them went from four copies to one body plus a table of kinds. That is what lets the
next client page be composed instead of copied. A yes closes the piece and the merge follows; a no
names the screen that moved, and the step that touched it is reopened.
