# Three commands for a local environment

## At a glance

A working copy on one Mac — the app, its data, a demo tenant — exists already, but only **inside one
process**: `pnpm stack` builds, brings up and tears down in one `runUp` call, and its data folder
dies with the shell that started it (`scripts/src/cli.ts#L91-L116`, `scripts/src/stack.ts#L109-L199`).
So there is no "it is up now" to come back to, and nothing to seed *into* from another terminal. The
cheapest safe path is not a fourth copy of any of this: it is **one more lifetime** for what exists.
`withStack`'s body becomes `startStack`, which hands back the same `RunningStack` plus a `stop`, and
`withStack` becomes `startStack` + the `finally` it has today — one path, two callers. A new
`pnpm local` command then writes what the run chose (ports, keys, pids, data folder) into one handle
file, and `up`, `seed` and `down` read it. The seed takes the target from the environment, exactly as
`runRidge` already does (`scripts/src/ridge.ts#L124`), so the same path serves ridge later. Price:
about 45 machine minutes and one new file of commands.

## The slice

One slice, walkable when it ends. In the human's own terminal:
`pnpm local up` leaves c-storage, the BFF and the front standing and prints the front's address, the
demo tenant's login link and the root's first password; `pnpm local status` reads them back and says
what is up; `pnpm local seed acme` makes a second tenant with a skeleton of records and prints its
link and passwords; `pnpm local down` stops all three and deletes the data, and then
`pnpm local status` reads back nothing — no folder, no process, no port, no handle.

**What is already there, and is therefore not built.** c-storage on a fresh SQLite file, the BFF's
service registered with a super-admin key the BFF never holds, the front, the seed door, and the
operator plus three tenants (`demo`, `hoa-sen`, `binh-an`, `shared/src/demo.ts#L112-L116`) all come
up today in `withStack` (`scripts/src/stack.ts#L117-L195`). A tenant is a first-class record the
product already makes through its own create (`createClient`, used by `scripts/src/ridge.ts#L180`
and `scripts/src/generator.ts#L87`): **nothing is missing for a tenant to exist**, which is the one
thing worth saying before the steps.

**What each of the three commands extends, and the parameter it gains.**

| Command | Extends | Parameter it gains |
| --- | --- | --- |
| `pnpm local up` | `withStack` (`scripts/src/stack.ts#L109`) split into `startStack` + `withStack`, run from a new `src/local.ts` beside `runStack` (`scripts/src/cli.ts#L119`) | a data folder and three fixed ports given in, in place of `mkdtemp` (`#L115`) and three `freePort()` calls (`#L121`, `#L155`, `#L157`); `startProcess` gains `keepOnExit`, so the children outlive the command (`scripts/src/running/processes.ts#L47-L48`) |
| `pnpm local seed <code>` | `seedClient` (`scripts/src/generator.ts#L82`), today reachable only in-process or through the loopback seed door (`scripts/src/seeding.ts#L18-L42`) | a **tenant name** beside the code — `seedClient` hard-codes `DEMO_CONFIG.name` at `#L89` — and its **target from the environment** (`C_STORAGE_URL` plus the three keys, read by `readStorageEnv`, `scripts/src/ridge.ts#L124`), so one path serves the local handle and ridge's tunnel |
| `pnpm local down` | nothing: this is the lifetime that does not exist. It reuses `classifyProcesses` (`scripts/src/running/strays.ts#L34-L60`), today called only by the walks (`scripts/src/walks.ts#L168`) | the data folder and the pids from the handle |

**Why the seed's parameter is the environment and not a flag.** `ops/seed.sh#L6` says in its own
header: *"It makes no client and no password: the human makes each copy at /operator"* — and
`#L38` refuses any environment but ridge. That by-hand step at the operator screen is what the
shared environment's next milestone removes. `runRidge` already takes its whole connection from the
environment (`#L124-L132`) and already has `tenant <code> <name>`, which makes a **bare** tenant:
code, name, root password, no records (`#L177-L184`). So the seed written here is the filled version
of a command that exists, at the same seam, and `ops/seed.sh` gains the same subcommand later
without a line of it being local.

**Ports, fixed on purpose.** Five ops scripts already reserve 3181 as "the local stack's port" and
refuse to use it (`ops/check.sh#L24`, `ops/seed.sh#L30-L32`), and nothing has ever bound it: the
local stack picks free ports. This piece makes that reservation true — c-storage 3181, the front
3180, the BFF 3182, the seed door 3183 — so the human bookmarks one address and three commands find
each other. The front must be `localhost:<port>`, since a passkey is bound to a name
(`scripts/src/stack.ts#L152-L156`).

**`ops/stack.sh` is not in this piece.** It is CloudFormation — `network | github | env <name>`
(`ops/stack.sh#L21`) — and shares only a word with `pnpm stack`.

## The steps

1. **The handle, and a stack that outlives its command.** Split `withStack` into `startStack`
   (returns `RunningStack & { stop }`) and today's `withStack` over it; add `keepOnExit` to
   `startProcess`; add `src/local.ts` with `up` only, writing `<credo root>/.local-env/handle.json`
   (git-ignored, 0600: it holds c-storage's keys). **Done when** `pnpm local up` returns to the
   prompt, the handle file exists, and `curl -sS -o /dev/null -w '%{http_code}' http://localhost:3180/`
   answers 200 in a *second* shell. ~10 min.
   *Built 2026-11-10 (the human's reading of the done-when is still owed):* `startStack` returns the
   stack plus `facts` (ports, pids, keys) and a `stop` that removes nothing; `withStack` is
   `startStack` plus today's `finally`; `startProcess` gains `keepOnExit`; `pnpm local up` writes
   `.local-env/handle.json` (0600, never over an existing one). **Correction to this step:** the
   front and the seed door are servers *inside* the starting process, not children
   (`scripts/src/stack.ts`), so `keepOnExit` on c-storage and the BFF alone would leave the front
   dead the moment `up` returned. `up` therefore builds, then starts one *keeper* process
   (`pnpm local keep`, detached through `keepOnExit`) that holds all four parts, writes the handle
   once up and takes the stack down on a signal; `up` waits for the keeper's `listening` and the
   front's answer, then prints and exits. The handle names the keeper's pid beside c-storage's and
   the BFF's: step 5's `down` signals the keeper first. *Evidence:* `pnpm --filter @credo/scripts
   check` ends `== exit 0` (steps all 0; 364 tests, coverage 100 %), logs/2026-11-10-133719-gate-scripts.log.
   In-process stand-ins only: `stack.test.ts` (case 1, a real stack on given ports, stopped in the
   test, data folder left), `processes.keep.test.ts` (case 3, a starter that exits while its child
   lives, killed in the test; red once by removing the `keepOnExit` guard), `local.test.ts` (case 4,
   and `up`/`keep` on stand-ins). **Owed to the human, in their terminal:** the done-when itself
   (`pnpm local up`, then `curl` from a second shell) and the keeper outliving its shell.
2. **The reading that says it is up, and the taken port.** `pnpm local status` prints one line a
   part: c-storage, the BFF, the front, the seed door — each `up` only on its own health answer, the
   way `waitUntilUp` already proves an answer is the child's own and not a stranger's on the port
   (`scripts/src/running/processes.ts#L69-L87`). `up` refuses a taken port by name, as
   `refuse_taken_port` does for the ops scripts (`ops/lib.sh#L546-L548`), and says which command to
   run. **Done when** `pnpm local status` prints four `up` lines, and a second `pnpm local up`
   refuses with the port named and changes nothing. ~7 min.
   *Built 2026-11-10 (the human's reading is deferred with step 1's, until `down` exists):*
   `status` prints a line a part (`c-storage`, the BFF, the front, the seed door), `up` only when
   the part answers its own way on its port (200 on the health routes and the front, the door's
   404 to a GET) **and** the process the handle names for it runs: the front and the door are the
   keeper's. A handle-less run says nothing is up (exit 0); any part down is exit 1. `up` binds
   each of the four ports before building, names every taken one with its part, and refuses with
   exit 2 and `run pnpm local status`; a standing handle is refused the same way. It names
   `status`, not `down`, because `down` is step 5. Waiting for the part's own `listening` line, as
   `waitUntilUp` does, was not usable here (the log belongs to a process that may be gone); a
   running pid beside the answer is the stand-in for it. *Evidence:* `pnpm --filter @credo/scripts check` ends `== exit 0` (370 tests, coverage 100 %), logs/2026-11-10-134247-gate-scripts.log; reds
   once by mutation: pid-only `up` reddened the two no-answer cases, dropping the port check
   reddened the taken-port case.
3. **The seed, parameterised by environment.** `seedClient` gains a `name`; `local seed <code>
   [<name>]` reads its target from the environment when given one and from the handle otherwise, and
   prints the tenant's login link, the root's first password and the people's. **Done when**
   `pnpm local seed acme` prints the link and `pnpm local status` counts four tenants, and the same
   command with `C_STORAGE_URL` and the three keys exported seeds without reading the handle at all.
   ~10 min.
   *Built 2026-11-10 (the human's reading is deferred with step 1's, until `down` exists):*
   `pnpm local seed <code> [<name>]` calls `seedClient`, which gained a `name` (the tenant's index
   and its config both carry it; the data set's own when none is given). The target is the
   environment when `C_STORAGE_URL` is set (`readStorageEnv`'s four keys and `APP_ORIGIN`, as
   `runRidge` reads them) and the handle otherwise; nothing after that choice knows which. It
   prints `<origin>/login?client-code=<code>`, the root's first password and each person's.
   `status` gained a `tenants: N` line, read through the handle's own keys. A code already held
   still ends in `seedClient`'s existing refusal, as exit 1 for now; step 4 makes it exit 2.
   **What changes to run this same path against the deployed environment:** only that the
   caller exports the tunnel's `C_STORAGE_URL` and the three keys plus the real `APP_ORIGIN`
   (`ops/lib.sh`'s `ridge_cli` already does so, without the AWS role) and that `ops/seed.sh` gains
   a `seed` subcommand that calls it and sends the printed passwords to the terminal alone, as
   `show`; this command prints them to `out`, which a deploy log would keep. Its removal on the
   deployed side is still the console's press: `untenant` stays fenced, untouched.
   *Evidence:* `pnpm --filter @credo/scripts check` ends `== exit 0` (374 tests, coverage
   100 %), logs/2026-11-10-135534-gate-scripts.log; its first run was red at knip alone (an
   exported type nothing imported), logs/2026-11-10-135152-gate-scripts.log, fixed and rerun.
   Reds once by mutation: the environment branch off reddened the environment and refusal
   cases; the name ignored reddened the handle case.
4. **A second seed of the same code is refused.** `seedClient#L93` already throws *"the service
   already holds data: not seeded over"*; the command turns that into one plain line and exit 2, and
   names the code. **Refusing, not idempotent, and deliberately:** a tenant's records are a week of
   orders, deliveries and closes replayed on their own days (`scripts/src/generator.ts#L268-L367`),
   so "make it match" means reconciling a week, which is `applyAll`'s job on ridge, not a local
   command's. **Done when** the second run exits 2, names `acme`, and the tenant count is still
   four. ~5 min.
   *Built 2026-11-10 (the human's reading is deferred with step 1's, until `down` exists):*
   `seedClient`'s existing refusal is now a named error, `SeededAlready` (same message, so its
   callers read as before), and `local seed` turns it into one line,
   `<code> is a tenant here already: nothing was seeded and nothing was changed`, exit 2; any
   other failure stays exit 1. *Evidence:* `pnpm --filter @credo/scripts check` ends `== exit 0`
   (375 tests, coverage 100 %), logs/2026-11-10-140620-gate-scripts.log (the gate waited about
   eight minutes on other gates and the load); the test seeds `acme` twice on in-memory storage,
   reads exit 2, the code named, no output, every record unchanged and one client; red once by
   mutation: with the named-error branch off the case ends exit 1.
5. **The teardown, proved by what is read back after it.** `down` stops the pids from the handle,
   removes the data folder and the handle, then **reads back** and prints a line a thing:
   no `credo-stack-*` folder under the temp folder, `classifyProcesses` finding none of credo's,
   nothing answering on the four ports, no handle. A reading that still finds something ends red and
   names it — the exit code never stands in for the read-back. **Done when** `pnpm local down`
   prints four cleared lines, `pnpm local status` says nothing is up, and `ls -d $TMPDIR/credo-stack-*`
   finds no match. ~10 min.
   *Built 2026-11-10 (the human's reading of the whole sequence, up, status, seed, down, is still
   owed):* `pnpm local down` asks the keeper, c-storage and the BFF to end (SIGTERM, never a kill),
   waits up to 10 s for each to be gone, removes `.local-env` (the data, the build, the keeper's
   log, the handle) and then reads back, a line a thing: the three processes, the four ports, the
   data folder with its database, the build folder, the handle. Anything found ends exit 1 with
   `down: NOT cleared:` and each thing named. Three guards: a handle whose data folder is not
   exactly `.local-env/data` or whose pids are not numbers is refused (exit 2) before any signal
   or deletion; a pid is signalled only when its command line still is the stack's (a recycled
   number, or a command that cannot be read, is left alone and named); a process that will not go
   stops the removal and is named. No handle, a handle of dead processes and a missing data folder
   are cases with their own lines, each ending in a verdict. **Departures from this step:** the
   read-back does not call `classifyProcesses` (it needs `ps` and would count other runs'
   processes; the handle's own pids are read instead), and it does not look for `credo-stack-*`
   under the temp folder, which the local stack never makes (its folders are the three above).
   *Evidence:* `pnpm --filter @credo/scripts check` ends `== exit 0` (386 tests, coverage 100 %),
   logs/2026-11-10-142442-gate-scripts.log; its first run was red on one uncovered branch,
   logs/2026-11-10-142151-gate-scripts.log, fixed and rerun. Each guard red once by mutation: no

   process is ended and read gone in `local.test.ts`; the stack's own detached run is the human's.

## The skeleton the seed makes, and it is a proposal

`seedClient` already writes a whole demo tenant: the staff setup, a dozen people and one who left,
customers, products and drivers, then a week of orders, deliveries, cancellations and a driver's
close, each on its own day (`scripts/src/generator.ts#L123-L367`). **The proposal is to take that
set unchanged as `acme`'s skeleton** — one tenant, its root, its invited operator, and the handful of
records of each kind the screens list — because it is the one body of demo data every screen in this
repository is already drawn against. The numbers in it are the machine's call until a real client
asks, and they are a proposal, not a decision: a shorter week or fewer people is one argument of one
function away. No real person and no real company is named; the demo set's companies are invented.

## The human's points

1. **Three commands, and what they print.** At step 5 you will have four commands to run in your own
   terminal, in order: up, status, seed, down. What matters is whether the printed lines tell you
   what you need without opening a log — the front's address, the demo tenant's link, the root's
   password, and after `down`, four lines saying the data folder, the processes, the ports and the
   handle are gone. A yes means the shape is right. A no reopens step 5 and the wording changes, not
   the design.

2. **The skeleton's size.** `acme` comes up with one tenant, its root, an invited operator, and
   about a dozen people, a handful of customers, products and drivers, and a week of orders and
   deliveries — the same demo set every screen here is drawn against. A yes keeps those numbers. A no
   says which kind is too many or too few, and step 3 changes one function's data, not its shape.

3. **The seed's one path.** The seed command here takes its target from the environment, so the
   command you run against your Mac is the command the shared environment will run later against its
   own box, with different values in the environment and no second copy of the code. That is what
   removes the by-hand tenant-making at the operator screen that the last teardown had to redo. A
   yes confirms that is worth the extra seam now; a no makes the local seed local-only and leaves the
   shared environment's milestone its own piece.

## Hazards no gate catches

- **A sandboxed session cannot signal a process an earlier command started**, so every step's check
  that reads a running stack is **the human's to run in their own terminal**, and no step chains an
  up with a check of it in one invocation. The build steps' unit cases start and stop their own
  children inside one process, which is what makes them runnable here at all.
- **`up` may wait while c-storage and the UI build.** It prints, before it waits, how long it may
  wait and until what clock time read by `date` as it starts, then one line every 30 seconds: a
  silent wait cannot be told from a freeze.
- **No Docker and no browser** in any step. The front is a plain Node server
  (`scripts/src/running/front.ts`); nothing here opens a browser, and the human's own browser is
  what visits the printed address.
- **A detached stack is a stray by the walks' own definition.** `isCredos` matches c-storage built
  into a temp folder and `--import tsx src/main.ts` under the root
  (`scripts/src/running/strays.ts#L18-L29`), and `classifyProcesses` calls a process whose parent is
  1 a stray (`#L58`). A local env left up will therefore be reported as a stray by the walks'
  pre-run read. Step 5 names this in `ops/README.md` — `pnpm local down` before a walk run — and
  teaching the classifier about the handle is left out of this slice deliberately.
- **Removing a seeded tenant from the shared environment has no scripted path.** `untenant` refuses
  every code but the deploy check's own (`scripts/src/ridge.ts#L186-L197`), by design, since it has
  none of the console's gates. Locally that costs nothing — `down` deletes the one SQLite file — but
  when this seed runs against the shared environment, its undo is still the console's press. That is
  a finding, not this piece's work.
